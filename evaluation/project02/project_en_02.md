# Projects

> ### AI Usage Regime: CONDITIONED AI (IA CONDICIONADA)
>
> *In compliance with Universidade de Aveiro institutional guidelines (Framework for Learning Assessment in the Age of Artificial Intelligence):*
>
> * **Software Development:** AI systems may be used as technical assistance for debugging or suggesting boilerplate/repetitive code. The core logic and solution architecture cannot be generated by AI (the *"one-shot"* generation of the entire project is strictly prohibited).
> * **Project Report:** The use of AI is permitted exclusively for linguistic proofreading and improving text clarity. Argumentative structure, interpretation of results, and conclusions must be the original intellectual work of the students.
> * **Mandatory Declaration:** The report must include the corresponding **AI Usage Declaration** (see template in the [Appendix](#appendix-ai-usage-declaration-template)), accompanied by excerpts of the most relevant prompts and a critical justification of accepted or rejected suggestions.

Form groups of two or three students (exceptionally, projects may be done individually) and select **one** of the following projects. All projects will be hosted on **GitHub**, using a private repository created by each group on a free personal account. See [here](#github-repository-setup-and-management) for details.

The repository must contain all source code, relevant scripts, configuration files (`Dockerfile`, `docker-compose.yml`, etc.), an *open-source* license file (`LICENSE`, e.g., MIT), and a `README.md` with clear instructions on how to run the project.
It must also contain the **project report in `PDF` format**, **compiled from Markdown (via Pandoc) or LaTeX**, including its source files (`.md`/`.tex`) in the repository.

This is a three-week project (with submission and **in-person presentation in the last class of the semester**, in December 2026). You have one week to notify your instructor (via e-mail) of your group members, class, and chosen topic (the list of topics can be found [here](#topics)). Upon notification, instructors will confirm your **group number**.

Do not hesitate to contact your instructor with any questions.
Additional instructions may be added.

## Topics

### 1. "Markdown to PDF" Web Service
* **Description:** Implement a web application in **Docker Compose** (two containers) that allows users to edit, preview, and convert Markdown documents into PDF files through the browser.
  1. **Compilation Backend (Python/FastAPI + Pandoc):** Create a container with Python/FastAPI and **Pandoc** (using a lightweight base image such as `pandoc/latex` or Pandoc + `weasyprint` to avoid heavy builds). The API must expose a `POST /api/convert` endpoint that receives an `.md` file (or Markdown text), generates the corresponding PDF (saving it to a **volume**), and returns the file for download (or a clear error message if conversion fails).
  2. **Web Frontend (HTML5/CSS3/JS on Nginx):** Build a web interface with a **Markdown text editor featuring real-time HTML preview** (e.g., using a lightweight JS library such as `marked.js`) and/or `.md` file upload, sending the conversion request via JavaScript (`fetch`) to download the generated PDF.
  3. **Optional Extensions (Creativity):** Output format selection (*PDF Report* vs. *Beamer Slides*), a history list of converted PDFs, or routing behind an **Nginx Reverse Proxy**.
* **Key Topics:** Docker Compose (multi-service), REST APIs (FastAPI + CORS), asynchronous JavaScript (`fetch`, DOM manipulation), document compilation (Markdown, Pandoc & LaTeX), Nginx, and `volumes`.

### 2. Interactive Geo-Data Dashboard (Weather, Mobility, or Environment)
* **Description:** Build a *web dashboard* in **Docker Compose** (two containers) to visualize georeferenced data on an interactive map (e.g., weather, air quality, bike-sharing stations, or traffic incidents).
  1. **Data Backend (Python/FastAPI + Pandas/Polars):** Develop an API that reads a real CSV dataset (with `lat`/`lon` coordinates, e.g., open data from `dados.gov.pt`) or queries a free public API without complex registration (e.g., **Open-Meteo**, with simple JSON file caching in a **volume**). The service must clean invalid records or missing values and expose the data as **JSON** on a REST endpoint (e.g., `GET /api/data`), supporting at least one filter parameter (e.g., category or region).
  2. **Geographic Frontend (HTML5/CSS3/JS + Leaflet on Nginx):** Create a web interface that consumes the API via `fetch()`, displays points on an interactive **Leaflet** map (with markers and informative popups), and allows dynamically filtering the visible markers on the page.
  3. **Optional Extensions (Creativity):** Complementary statistical chart (**Matplotlib/Seaborn** or a JS library), marker clustering, or deployment via **Nginx Reverse Proxy**.
* **Key Topics:** Web Programming (HTML5/CSS3/JS, DOM, `fetch`, Leaflet), REST APIs (FastAPI + CORS), data cleaning and formatting (CSV/JSON with Pandas/Polars), Nginx, and Docker Compose.

### 3. CSV Analysis and Visualization Web Service (*CSV Data Explorer*)
* **Description:** Create a web platform in **Docker Compose** (two containers) that lets users upload any CSV file and automatically view descriptive statistics and plots of its columns.
  1. **Analytical Backend (Python/FastAPI + Pandas/Polars + Matplotlib/Seaborn):** Implement an API with a `POST /api/upload` endpoint that receives a CSV file, stores it in a **volume**/temporary directory, handles missing values, and returns a JSON statistical summary of numeric columns (`count`, mean, min, max) along with the list of available columns. A second endpoint (e.g., `GET /api/plot/{column}`) reads the stored CSV and generates the corresponding chart as a PNG image.
  2. **Interactive Frontend (HTML5/CSS3/JS on Nginx):** Build a web page with an upload form (`fetch` with `FormData`), a dynamic statistical summary table generated in the DOM, and buttons/selectors to open and view the plot for each column without reloading the page.
  3. **Optional Extensions (Creativity):** Outlier detection (**IQR** method), correlation matrix (**Seaborn heatmap**), chart type selection (histogram vs. boxplot), or **Nginx Reverse Proxy**.
* **Key Topics:** REST API file uploads (FastAPI + CORS), data analysis (Pandas/Polars), visualization (Matplotlib/Seaborn), dynamic DOM manipulation (`fetch`), Nginx, and Docker Compose.

### 4. Dynamic Full-Stack Portfolio
* **Description:** Build a personal portfolio website in **Docker Compose** (two containers) that fully separates content from presentation, simulating a modern *Micro-CMS* with real persistence.
  1. **REST Backend with Persistence (Python/FastAPI):** Create an API that exposes portfolio data as JSON (`GET /api/profile` with name, bio, skills, and project list with tags), accepts submissions at **`POST /api/contact`** (validating fields and storing received messages in a JSON file or SQLite inside a Docker **volume**), and provides `GET /api/messages` to verify persisted messages during the demo.
  2. **Semantic & Interactive Frontend (HTML5/CSS3/JS on Nginx):** Develop a page using semantic HTML5 and CSS3 (*Box Model*) that dynamically loads API data via `fetch()`/`async`/`await`, allows **filtering projects by category/tag** in the DOM, includes a **Dark/Light** theme toggle (saved in `localStorage`), and provides a contact form with client-side validation and visual submission confirmation.
  3. **Optional Extensions (Creativity):** Dynamic addition/editing of projects via API, a visual panel of submitted messages, or deployment behind an **Nginx Reverse Proxy**.
* **Key Topics:** Asynchronous JavaScript (`fetch`/`async`/`await`, DOM manipulation, `localStorage`), semantic HTML5 & CSS3, REST APIs with persistence (FastAPI + CORS), Nginx, and Docker Compose.

### 5. Real-Time Telemetry Station (MQTT + WebSockets)
* **Description:** Develop an event-driven real-time telemetry architecture in **Docker Compose**, integrating metric collection, the **MQTT** protocol, and a live-updating web dashboard.
  1. ***Pub/Sub* Broker (Eclipse Mosquitto in Docker):** Configure the **Mosquitto** broker with two listeners: TCP (`1883`) for Python clients and **WebSockets (`9001`)** for the browser, using clear hierarchical topics (e.g., `iei/telemetry/system`).
  2. **Publisher Agent (Python + `paho-mqtt` + `psutil`):** Implement a script (running on the host machine connected to `localhost:1883` or in a dedicated container) that periodically collects real machine metrics (CPU and RAM usage) — or simulated environmental sensors — and publishes them in **JSON**, including a ***Last Will and Testament* (LWT)** message to signal abrupt disconnections.
  3. **Real-Time Web Dashboard (Nginx + HTML5/CSS3/JS):** Build a web page that connects to the broker over **WebSockets**, subscribes to MQTT topics, updates values in the DOM in real time, and displays a visual alert when a threshold is exceeded (e.g., CPU/RAM $> 80\%$) or when an LWT event arrives.
  4. **Optional Extensions (Creativity):** Python subscriber that logs history to CSV in a volume and generates trend plots with Pandas/Matplotlib.
* **Key Topics:** *Publish/Subscribe* & MQTT (Mosquitto, topics, QoS, LWT), browser WebSockets, dynamic DOM manipulation, telemetry (`psutil`), Nginx, and Docker Compose.

### Evaluation Criteria Details

#### 1. Technical Implementation and Requirements (6.0 points)
* The system fully meets the core requirements described in the chosen topic.
* Absence of runtime errors, unhandled CORS blocks, or broken dependencies.
* Proper use of Docker Compose, `volumes`, environment variables, and clean service configuration.

#### 2. Technical Report (Markdown/LaTeX) and Reproducibility (3.0 points)
* The report (in **PDF** format, **compiled from Markdown with Pandoc or LaTeX**, with source files versioned in the repository) must be **concise and structured (recommended: 4 to 6 pages, excluding appendices)**:
  * **Introduction & Context:** Problem description, objectives, and technologies used.
  * **Solution Architecture:** Conceptual diagram (containers, ports, HTTP/MQTT flows, and volumes) and justification of technical decisions.
  * **Tests & Results:** Empirical demonstration of functionality (screenshots, sample JSON responses/generated plots).
  * **Difficulties & Conclusions:** Honest reflection on technical obstacles overcome and lessons learned.
* The `README.md` file at the repository root must allow any evaluator to clone and run the project with direct, reproducible instructions, accompanied by a `LICENSE` file.

#### 3. Project Presentation and Live Demo (3.0 points)
* Mandatory in the **last class of the semester** with participation from all group members:
  * **Presentation & Visual Support:** Clear, objective, and structured presentation of the problem, implemented architecture, and main results (with strict time management).
  * **Live Working Demo:** Practical execution of the solution (in Docker containers) demonstrating core requirements and system responses to test cases.
  * **Technical Mastery & Q&A:** Ability of each group member to explain architectural choices, submitted code, and critically answer instructors' questions.

#### 4. Critical and Conditioned Use of Artificial Intelligence (4.0 points)

Generative Artificial Intelligence (e.g., Gemini, ChatGPT, Claude) is permitted as a **learning support tool**, under strict rules of transparency, human oversight, and engineering best practices:

* **Permitted Uses:** Support in architecture design, assistance in debugging syntax or configuration errors (Nginx, FastAPI, CORS, JS, LaTeX), improving report writing, and brainstorming test cases.
* **Strictly Prohibited Uses:** *"One-shot"* generation of the entire project or report without human understanding and validation. Submitting code that team members cannot justify or explain in detail is strictly forbidden.
* **Context Engineering and Agent Best Practices:**
  Continuing and evolving the techniques introduced in **Class 02** will be positively evaluated:
  * **`AGENTS.md` File:** Creating and maintaining an `AGENTS.md` file at the repository root defining project context, coding conventions, architecture, and security boundaries.
  * **Definition of *Skills* and Guardrails:** Modular rules constraining AI suggestions to verifiable, safe commands.
  * **Structured Prompt Engineering:** Demonstration of iterative prompts with bounded context, rather than vague or naive requests.
* **Mandatory Report Section ("AI Usage Declaration"):**
  The report must include the structured institutional declaration (see [Appendix](#appendix-ai-usage-declaration-template)), accompanied by excerpts of the most relevant prompts and critical reasoning on why AI suggestions were **accepted, adapted, or rejected** (e.g., *"the AI suggested setting `Access-Control-Allow-Origin: *` in FastAPI, but we restricted it to our frontend origin at `localhost:8080`"*).

#### 5. Creativity and Additional Features (2.0 points)

This criterion rewards groups that go beyond minimum requirements and demonstrate technical autonomy:

* **Examples of merit:**
  * Implementation of the **optional extensions** listed in the chosen topic (e.g., **Nginx Reverse Proxy** unifying `/` and `/api/`, IQR outlier detection, correlation heatmap, or persistent history).
  * Automated API tests (e.g., `pytest` / `curl` scripts) and *healthchecks* in `docker-compose.yml`.
  * Superior visual polish, accessibility (*a11y*), and mobile-responsive design.
  * Automated report compilation (e.g., `Makefile` or *GitHub Actions* to build the PDF).

#### 6. Collaborative Workflow, Task Management, and Git (2.0 points)

* **Task & Issue Management:** Active use of **GitHub Issues** (and optionally GitHub Projects/Kanban) to plan, assign, and track team progress.
* **Branch & Pull Request Workflow:** Development on *feature branches* and integration into `main` via **Pull Requests** reviewed and approved by another team member.
* **Traceability & Work Distribution:** Linking commits and PRs to corresponding issues (e.g., `closes #4`), with visibly balanced effort across all members.
* **Repository Hygiene:** Atomic, descriptive commit messages (e.g., *Conventional Commits*), strict `.gitignore` (no `node_modules`, `__pycache__`, `.venv`, credentials, or temporary files), and presence of the `LICENSE` file.

## GitHub Repository Setup and Management

Here are the instructions to set up your team's private GitHub repository for Project 02.

### 1. Repository Creation (ONLY ONE group member)

Once instructors confirm your team and assign your **group number**:

1. **Access GitHub:** Log in at [github.com](https://github.com).
2. **Create New Repository:** Click **New** (or the `+` menu in the top-right corner).
3. **Repository Name:** Must strictly follow this naming convention (lowercase):
   `iei-2026-p2-[class]-g[group]`
   *(Example for class TP1, group 3: `iei-2026-p2-tp01-g03`)*
4. **Visibility:** Must be set to **Private**.
5. **Initialization:** You may initialize with a `README.md`, select an appropriate `.gitignore` (e.g., Python), and pick an *open-source* license (`LICENSE`, e.g., MIT License).
6. **Create:** Click **Create repository**.

-----

### 2. Adding Collaborators (Team Members and Instructors)

Because the repository is **private**, you must grant access to your teammates and the course instructors for supervision and grading:

1. In your repository, go to the **Settings** tab.
2. In the left sidebar, click **Collaborators**.
3. Click the green **Add people** button.
4. **Add teammates:** Enter each teammate's GitHub username or e-mail and send an invitation with **Write** permissions.
5. **Add instructors:** Enter the instructors' GitHub usernames (provided in class and on Moodle) and send the invitation.
6. All invited users must accept the invitation via e-mail or directly on their GitHub home page.

-----

### 3. SSH Key for Access (If not already configured in Project 01)

If you already configured an SSH key on your GitHub account during Project 01, you can proceed directly to `git clone`. Otherwise:

1. **Check or generate an SSH key:**
   ```bash
   cat ~/.ssh/id_ed25519.pub
   ```
   If the file does not exist, generate a new key and read the public key:
   ```bash
   ssh-keygen -q -t ed25519 -N ''
   cat ~/.ssh/id_ed25519.pub
   ```
2. **Add to your GitHub account:** Go to **Settings $\rightarrow$ SSH and GPG keys $\rightarrow$ New SSH key**, give it a descriptive title (e.g., `Laptop-IEI`), paste the public key with type **Authentication Key**, and click **Add SSH key**.
