# Projects

> ### AI Usage Regime: CONDITIONED AI (IA CONDICIONADA)
>
> *In compliance with Universidade de Aveiro institutional guidelines (Framework for Learning Assessment in the Age of Artificial Intelligence):*
>
> * **Software Development:** AI systems may be used as technical assistance for debugging or suggesting boilerplate/repetitive code. The core logic and solution architecture cannot be generated by AI (the *"one-shot"* generation of projects is strictly prohibited).
> * **Project Report:** The use of AI is permitted exclusively for linguistic proofreading and text clarity. Argumentative structure, interpretation of results, and conclusions must be the original intellectual work of the students.
> * **Mandatory Declaration:** The final report must include the institutional **Declaration of AI Usage** (see template in [Appendix](#appendix-declaration-of-ai-usage-template)), accompanied by excerpts of the most relevant prompts and critical justification for accepted or rejected suggestions.

Form groups of two or three students (exceptionally, projects can be done individually) and select **one** of the following projects. All projects will be hosted on **GitHub**, using a private repository created by each group on a free personal account. Check [here](#github-repository-setup) for details.

The repository must contain all relevant scripts, configuration files, and a `README.md` with instructions on how to deploy the project.
It should also contain a project report in `PDF` format.

This is a three-week project. You have one week to notify your professor (via e-mail) of your group members, your lab class (turma), and your chosen topic (the list of topics can be found [here](#topics)). Following this notification, professors will assign your official **group number**.

Do not forget to contact your professor with any questions.
Further instructions may be added.

## Topics

### 1. High-Performance Static Site with Caching
* **Description:** Deploy a high-performance web service using **Docker Compose**. This architecture must orchestrate two interdependent services within an internal network: a backend web server (such as **NGINX**, **Caddy**, or **Apache `httpd`**) and a high-performance reverse proxy cache in front (such as **Varnish Cache** or **NGINX** in proxy cache mode). The static website content (a rich page with CSS styles, scripts, and images) must be served from a **volume** mounted into the web server container. Only the cache service port should be exposed to the outside. Furthermore, students must conduct load and performance benchmarks from the command line (using tools like `ab` — Apache Benchmark or `wrk`), comparing latency and throughput (*requests/sec*) with and without the cache enabled.
* **Core Topics:** Docker Compose (multi-service), web servers (NGINX/Caddy/Apache), Varnish Cache, internal container networks, `volumes`, CLI performance and latency benchmarking (`ab`/`wrk`).

### 2. The "It Works on My Machine" Solver: Containerized Development Environment
* **Description:** Create a hermetic and reproducible container-based development environment for a chosen programming language (e.g., Python, C/C++, Rust, or Node.js), eliminating local dependency conflicts.
  1. **Environment Setup:** Create an optimized `Dockerfile` with the compiler/interpreter, static analysis tools (*linters*), and non-root user support (avoiding host file permission issues).
  2. **Development with Volumes:** Use Docker Compose and **volumes** (*bind mounts*) so that source code is edited directly on the host machine while compilation, execution, and testing occur in complete isolation inside the container.
  3. **Automation & Sample Application:** Provide a small test application (with functions and corresponding unit tests) and a CLI automation script (or `Makefile`) to compile, run tests, and generate linting reports inside the container with a single command.
  4. **IDE Integration (Optional / Challenge):** Teams may optionally adopt the open specification of [Development Containers (containers.dev)](https://containers.dev) by configuring a `.devcontainer/devcontainer.json` file for automatic integration with Visual Studio Code.
* **Core Topics:** `Dockerfile`, development environment isolation, Docker Compose, `volumes`, package management (`apt`), non-root permissions, test automation, and [containers.dev](https://containers.dev) specification.

### 3. Gemini Desktop Assistant: Sandboxed GUI App with Flatpak
* **Description:** Implement a desktop graphical application (GUI) in Python that allows users to interact with **Google Gemini language models via API**, packaging and distributing it via a **Flatpak** application container.
  1. **Minimalist Graphical Interface:** The application should feature a simple and functional GUI (built using the standard library **Tkinter**, without requiring complex styling, or alternatively with **CustomTkinter**/**PyGObject**): a text field for the user prompt, a submit button, and a scrollable area displaying the model's response.
  2. **API Consumption & Secrets:** The application must communicate with the Gemini API (using HTTP headers with the secure `GEMINI_API_KEY` environment variable or an in-app setup dialog), handling network failures and API errors gracefully.
  3. **Flatpak Packaging & Manifest:** Create the Flatpak build manifest (`yaml` or `json`) defining the runtime/SDK (e.g., `org.gnome.Platform`), required modules, `.desktop` file integration, and application icon.
  4. **Permission Audit in Report:** Demonstrate strict sandbox isolation (bubblewrap) adhering to the principle of least privilege, documenting the application's behavior with and without the network permission (`--share=network`) and verifying that access to host sensitive files (e.g., `~/.ssh`) is strictly blocked.
* **Core Topics:** Graphical User Interfaces (Python/Tkinter), REST API consumption (Gemini), Application Containers (Flatpak), Desktop Sandboxing & Permissions (`finish-args`, `--share=network`, display sockets), desktop integration (`.desktop`).

### 4. Web Platform with State Management and Automated Backups
* **Description:** Deploy a full-fledged database-driven web platform (such as **WordPress** or **Ghost CMS**) using **Docker Compose**. The project requires securely orchestrating the web application and database (**MySQL** or **MariaDB**) containers in an isolated network, with full persistence through **volumes**. In addition to configuring and personalizing the platform (with initial posts), the group must create a **Bash automation script** that performs consistent database (`mysqldump`) and media file backups, producing timestamped `.tar.gz` archives with automatic rotation (keeping the last $N$ backups) along with a restore/disaster-recovery script.
* **Core Topics:** Docker Compose (multi-service), WordPress/Ghost, relational databases, internal networking, `volumes`, environment variables (`.env`), Bash backup & disaster recovery scripting (`mysqldump`, `tar`, `cron`).

### 5. Performance Showdown: Virtual Machine vs. Container
* **Description:** Conduct a rigorous comparative performance study between traditional virtualization and containerization. The group must deploy an identical **NGINX** web server in two environments: 1) inside a full **Debian Virtual Machine** (configured via VirtualBox or QEMU) and 2) inside a **Docker container**. Subsequently, students must run a benchmark suite collecting objective system metrics: boot/startup time (`systemd-analyze` or stopwatch), idle and loaded RAM footprint (`free`, `vmstat`, `docker stats`), disk storage usage (disk image size `.vdi`/`.qcow2` vs Docker image layers), and HTTP request latency under stress using benchmarking tools (`ab` or `wrk`). The final report must include tables, comparative charts, and an in-depth architectural discussion of the findings.
* **Core Topics:** System virtualization (VirtualBox/QEMU), Containers (Docker), resource monitoring (`top`, `free`, `df`, `time`), network benchmarking (`ab`/`wrk`), comparative architectural analysis.

### 6. Observability Cockpit: Container Monitoring with Prometheus & Grafana
* **Description:** Deploy a complete container observability and telemetry infrastructure using **Docker Compose**. The architecture must integrate three orchestrated services:
  1. **cAdvisor:** An agent that gathers resource usage telemetry (CPU, RAM, network traffic, and disk I/O) directly from the Docker daemon by mounting the `/var/run/docker.sock` socket.
  2. **Prometheus:** A time-series database server configured to periodically scrape metrics exposed by cAdvisor over an isolated internal network.
  3. **Grafana:** A web visualization dashboard connected to Prometheus as a data source, configured as the only service exposing a port to the host/outside world.
  The team must create an interactive Grafana *dashboard* showcasing real-time system container metrics and demonstrate its effectiveness by generating a CPU/memory load spike on a separate benchmark container (using tools like `stress` or `stress-ng`).
* **Core Topics:** Docker Compose (multi-service), observability and telemetry (Prometheus, Grafana, cAdvisor), private container networks, host socket mounting, metric persistence in `volumes`, stress testing.

## Evaluation Criteria

The project will be evaluated on a scale of **0 to 20 points**, distributed across five core vectors:

| Evaluation Vector | Weight | Score | Main Description |
| :------------------------ | :--------: | :---------: | :---------------------------------------------------- |
| **1. Technical Implementation & Requirements** | 30% | 6.0 pts | Rigorous compliance with functional requirements, error-free operation, modular architecture, and best practices (Docker/Compose/Flatpak/Bash). |
| **2. Technical Report & Documentation** | 30% | 6.0 pts | Clarity, logical structure, and technical depth of the PDF report; high-quality, reproducible setup instructions in `README.md`. |
| **3. Critical & Transparent Use of AI** | 20% | 4.0 pts | Context engineering (`AGENTS.md` file, modular *skills*), prompt relevance, critical justification of accepted/rejected suggestions, and AI Declaration. |
| **4. Creativity & Additional Features** | 10% | 2.0 pts | Innovation and extension beyond baseline requirements (extra features, failure resilience, UX/visual polish, auxiliary automation scripts). |
| **5. Collaborative Workflow & Project Management** | 10% | 2.0 pts | Active use of GitHub Issues/Tasks, feature branch/PR review workflows, atomic commit history, and balanced team member contributions. |

---

### Evaluation Vector Details

#### 1. Technical Implementation and Requirements (6.0 points)
* The system fully meets all functional specifications described in the chosen topic.
* Absence of broken dependencies or abnormal behavior.
* Proper usage of volumes, isolated networks, environment variables, and security boundaries.

#### 2. Technical Report and Reproducibility (6.0 points)
* The report (in PDF format) must be well-structured and include:
  * **Introduction & Problem Statement:** Context and core objectives of the project.
  * **Architecture & Design:** Conceptual architectural diagrams and justification of engineering choices.
  * **Instructions & Empirical Tests:** Demonstration of operational functionality (including terminal outputs and screenshots).
  * **Difficulties & Conclusion:** Honest reflection on technical obstacles overcome and key takeaways.
* The repository's `README.md` must serve as an immediate quickstart guide, enabling anyone (including evaluators) to clone and deploy the project with a single command.

#### 3. Critical and Conditioned Use of Generative AI (4.0 points)
Generative AI (e.g., Gemini, ChatGPT, Claude) is welcomed as a **learning and development aid**, subject to strict transparency, human-in-the-loop validation, and modern engineering practices:
* **Allowed Uses:** Architecture brainstorming, syntax/configuration debugging assistance, report drafting polish, and test scenario ideation.
* **Strictly Prohibited Uses:** *"One-shot"* generation of entire projects or reports without human comprehension and validation. Submitting code that group members cannot explain or defend during evaluation is unacceptable.
* **Context Engineering & Agent Best Practices:**
  Direct application of techniques covered in **Class 02** will be positively evaluated:
  * **`AGENTS.md` File:** Creation and maintenance of an `AGENTS.md` file in the repository root, detailing project context, architectural guidelines, coding conventions, and safety constraints for AI assistants.
  * **Modular *Skills* & Guardrails:** Definition of modular skills or safe execution guardrails (*safe-cli* pattern) ensuring AI suggestions remain verifiable and safe for the development environment.
  * **Structured Prompt Engineering:** Evidence of disciplined, iterative prompting with bounded context rather than naive or vague single-sentence queries.
* **Mandatory Section in Report ("Declaration of AI Usage"):**
  The report must include the institutional declaration structured with the following fields:
  * **Tool(s) used:** Clear identification of the AI models and tools consulted (e.g., Gemini, ChatGPT, Claude, GitHub Copilot).
  * **Supported tasks:** Explicit breakdown of supported steps (e.g., syntax debugging in Dockerfile, test structure ideation, grammar proofreading).
  * **Human Verification:** Explicit confirmation that all code and text were manually tested, reviewed, and validated by the students.
  * **Responsibility:** Unequivocal statement that team members assume full responsibility for the final content and code submitted.
  * **Prompt Excerpts & Critical Reflection:** Presentation of excerpts of the most relevant prompts used and critical justification for why the team **accepted, adapted, or rejected** AI proposals (e.g., *"the AI suggested exposing database port 3306, but we rejected this to keep the database isolated on the internal Docker network"*).

#### 4. Creativity and Additional Features (2.0 points)
This vector rewards teams that go beyond baseline expectations and demonstrate engineering initiative:
* **Examples of extra credit:**
  * Automated testing pipelines and service healthchecks.
  * Enhanced security hardening (e.g., strict Linux capabilities, non-root users, encryption).
  * Superior user experience, intuitive CLI/GUI feedback, or visual polish.
  * Meaningful extra features that increase the real-world utility of the system.

#### 5. Collaborative Workflow, Task Management, and Git (2.0 points)
Collaboration and traceability are foundational to modern software engineering:
* **Task Management & Issues:** Active use of **GitHub Issues** (and optionally GitHub Projects/Kanban) to plan, assign, and track team progress.
* **Branching & Pull Request Workflow:** Development conducted on *feature branches* and integrated into `main` via **Pull Requests** reviewed and approved by another team member.
* **Traceability & Balanced Workload:** Linking commits and PRs to corresponding issues (e.g., `closes #3`), demonstrating a balanced distribution of work among all group members.
* **Repository Hygiene:** Atomic and informative commit messages (e.g., *Conventional Commits*), clean `.gitignore` configuration, and absolute prevention of secrets/API keys or unnecessary binaries in the repository.

## GitHub Repository Setup

Here are detailed instructions to set up your team's private repository on GitHub.

### 1. Repository Creation (ONE team member only)

Once the professors confirm your group and assign your official **group number**:

1. **Access GitHub:** Sign in to [github.com](https://github.com) (or create a free personal account if you don't have one).
2. **Create New Repository:** Click the **New** button (or the `+` menu in the top-right corner).
3. **Repository Name:** You must strictly follow this naming convention (in lowercase):
   `iei-2026-p1-[turma]-g[group]`
   *(Example for lab class TP1 and group 3: `iei-2026-p1-tp01-g03`)*
4. **Visibility:** You must select **Private**.
5. **Initialization:** You may check the option to add a `README.md` file and select a suitable `.gitignore` template (e.g., Python).
6. **Create:** Click **Create repository**.

-----

### 2. Add Collaborators (Team Members and Instructors)

Because the repository is **private**, you must grant access to your teammates and the course instructors for monitoring and evaluation:

1. Inside your new repository, open the **Settings** tab.
2. In the left sidebar, click **Collaborators**.
3. Click the green **Add people** button.
4. **Add teammates:** Enter the GitHub username or email of each group member and send the invitation with write permissions (*Write*).
5. **Add instructors:** Enter the GitHub usernames of the course instructors (provided during classes and on Moodle) and send the collaboration invite.
6. All invitees must accept the invitation received by email or on their GitHub homepage to access the repository.

-----

### 3. Configure an SSH Key for Access

This will allow you to clone, pull, and push to the repository from your command line without entering your password or personal access tokens every time.

1. **Check for an existing SSH key:**
   Open your terminal and run this command:

   ```bash
   cat ~/.ssh/id_ed25519.pub
   ```

2. **Generate a key (if needed):**

   * If you see a key (starting with `ssh-ed25519...`), copy the entire line and skip to step 3.
   * If you see an error like "No such file or directory," run the following command to generate a modern key:
     ```bash
     ssh-keygen -q -t ed25519 -N ''
     ```
   * After it is generated, view and copy your new public key:
     ```bash
     cat ~/.ssh/id_ed25519.pub
     ```

3. **Add the key to your GitHub account:**

   * Go to your personal GitHub account settings (**Settings** in the top-right profile menu).
   * On the left sidebar, click **SSH and GPG keys**.
   * Click the **New SSH key** button.
   * Give it a descriptive **Title** (e.g., "UA-Laptop").
   * Paste the public key you copied into the **Key** field.
   * Ensure that the "Key type" is set to **Authentication Key**.
   * Click **Add SSH key**.
